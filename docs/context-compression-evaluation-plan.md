状态：基于当前工作区完成只读核查和无网络探针验证；本文是实验方案，尚未实现上下文批量评测，也没有新增真实模型调用。已有 C01 结果不是压缩收益数据。本文不涉及 Team。

目标：验证“在明确任务范围和相同资源上限下，压缩是否降低完成任务的总开销，同时保住任务质量”。结果允许为负：压缩率高不代表成本低，成本低也可能只是任务更早失败。

**1. 目前掌握的事实**

- 现有 `evals` 实现 C01 文件读取偏移修复题的 validate/run/verify，具有源码快照、独立工作区、独立验收、逐调用记录、失败留证和校验和。可以扩展现有框架，不需要引入评测平台。
- 既有真实样本 `eval-results/20260918T074518Z-C01-live-b267fbe3`：任务通过，11/11 验收通过，12,797 ms，6 次主模型调用；摘要调用与 `context.compacted` 均为 0。只证明该题和执行链路跑通。
- 该样本来自当时冻结的源码，不能直接充当当前压缩实现的对照组。
- 既有确定性测试证明边界与协议行为；假模型长对话测试不能证明真实模型压缩后仍能正确续做，也不能换算真实降本比例。

**2. 先补测量链路，否则不能正式跑 A/B**

| 前置项 | 当前情况 | 最小完成标准 |
|---|---|---|
| 显式实验配置 | `evals/agent_adapter.py:87` 只给 ContextConfig 指定 summary_model，环境中的压缩开关未进入该配置 | profile 接收并冻结完整非敏感上下文配置；保存 Agent 实际生效值；确认两组差异仅为预定开关 |
| 摘要请求录制 | EvidenceSDK 缺少 with_options，而摘要客户端设置 timeout 后会调用它 | 包装返回的 SDK 仍录制，共享唯一请求编号；主调用、摘要调用及失败都能关联 call_id |
| 完整长历史证据 | 通用脱敏器限制列表 200 项、字典 200 项、深度 8 | 评测专用脱敏记录；保留完整可公开输入，或明确数量、遗漏范围、哈希及受控原件位置，禁止静默截断 |
| 上下文任务入口 | worker 只跑 C01 单次 agent.run(prompt) | 加入合法历史、同步磁盘状态、运行态、归档的 seed；支持多轮脚本及真实端到端任务 |

| 指标汇总 | 已有调用去重与分类型 usage，金额为空 | 补压缩与投影明细、总开销、验收约束、配对汇总；按实际供应商确认计费口径 |

无网络探针在本次核查得到：摘要路径报 `AttributeError: 'EvidenceSDK' object has no attribute 'with_options'`，底层 SDK 调用为 0；205 条消息经过录制所用脱敏器后仅剩 200 条，顶层没有 truncated 标记。应在修复后增加专门回归测试，再开始付费试跑。

现有 C01 profile 禁用 shell，并移除了 load_tool_output，不能承担长命令日志回读评测。新增 profile 应向所有对照组提供相同工具；如启用 shell，需要匹配的任务进程树清理与验收隔离，不能沿用“worker 不会产生工具子进程”的超时假设。

另一个已确认的能力边界：`codeagent/tools/bash.py:116` 会将超过 15,000 字符的命令输出提前裁为前 6,000 和后 3,000 字符。默认上下文单结果归档阈值是 80,000 字符，不能恢复在工具层已丢掉的中间文本。“完整历史”指 Agent 实际收到的历史。长日志题应让原命令把完整日志实际写入文件，或使用未被上游截断的历史证据；另留未落盘的负对照检验能否承认证据不足。不可用直接向 ContextManager 注入 100k mock 输出，宣称已验证真实 bash 日志的无损回读。

**3. 四个对照组回答不同问题**

| 组 | ContextConfig.mode | tool_projection_enabled | 用途 |
|---|---|---|---|
| A：基础保护 | off | false | 禁用自动历史压缩的基线 |
| B：只清理工具冗余 | off | true | 验证无需摘要模型的清理能贡献多少 |
| C：只做语义摘要 | model | false | 验证摘要的收益与代价 |
| D：当前组合 | model | true | 验证先清理、再按压力摘要的完整策略 |

上表是需要接入评测 profile 的配置，不是现有 CLI 已支持的参数。

四组都保留相同的硬预算、单次工具大输出保护和归档回读能力。因此 A 应称为“基础保护基线”，不能称“完全不处理上下文”。单独设置 mode=off 并不会关闭工具投影，更不能通过只设置当前 eval 未读取的环境变量构造 A 组。

固定历史从完整、尚未摘要的 seed 开始：summary_text 为空、compacted_message_count 与 summary_revision 为 0，没有旧摘要游标或失败冷却；保留与历史一致的工作区和任务事实。不能让 A 导入 D 已生成的摘要 checkpoint。恢复专项实验由各配置从共同起点生成自己的 checkpoint，再比较恢复行为。

先比较 A/D；再在预先选定的代表性任务子集补 B/C，用组件开关定位收益。如果 D 相比 B 没有可信增益却增加摘要开销，应保留 B 作为默认或收紧摘要触发条件。不要预设每个机制都值得保留。

若要证明“优于上一版本”，另冻结可以复跑的上一版本及输入；当前有大量其他未提交修改，直接比较 git HEAD 与当前目录会混入非上下文改动。

**4. 两条实验路线分别回答因果与实际效果**

固定历史续做：从同一份合法历史、同一工作区和同一运行态开始，在相同位置触发压力，让真实模型继续完成后续任务。它更容易定位信息丢失与压缩收益，但结果必须标为“固定历史续做”，不能冒充从零执行整项需求的成本。共享前缀的生成成本单列，续做成本单列。

端到端真实任务：从干净代码副本和需求开始，让 Agent 自己读取、修改、测试，直至结束或达到预算。A/D 后续走不同路线是实验结果的一部分；不能强行让它们调用同一串工具，也不能把某条旧轨迹的缩短比例当作真实任务提升。

离线回放只测确定性开销、触发条件、字符长度和档案体积；使用假摘要时不得报告语义保持率。三类结果分表呈现。

**5. 推荐任务：短任务保底，长任务证明价值**

每题先写验收，再看任何一组的结果。题目优先来自去敏后的真实开发任务；人为注入缺陷、构造日志、预置历史须标注来源。题库应包含当前项目以外的目标代码副本；只有本项目自建题时，结论限定于自建评测集。

| 类型 | 具体例子 | 独立验收 |
|---|---|---|
| 短任务对照 | 单文件 offset 修复或小参数校验，不人为塞入历史 | 目标用例修复、相关回归通过；记录是否发生不必要摘要及额外延迟 |
| 长检索后修改 | 在多模块项目定位一项配置传播缺陷，沿真实调用链修复 | 行为测试与兼容性检查通过；按请求记录历史增长、工具清理与摘要触发 |
| 用户中途改要求 | 最初导出 CSV，后明确改 JSON 且要求保留中文字段，随后继续开发 | 产物为 JSON、中文字段正确、旧 CSV 要求未回流；不能只搜索摘要是否出现 JSON |
| 日志中间的关键证据 | 原命令实际落盘的完整日志中间含特定错误路径与失败用例，首尾无答案；完成相关修复 | 修复对应行为且原回归通过；文件检索/归档回读作为诊断，不强制正确方案必须使用某个工具 |
| 已完成步骤与失败事实 | 历史及磁盘一致地表明第一阶段完成、第二阶段测试失败 | 保住第一阶段不变量，第二阶段修复；重复只读检查不判失败，重复副作用按计数器验收 |
| 多阶段跨文件任务 | 修改配置解析、执行逻辑和公开说明，并保留旧接口 | 端到端与旧接口验收同时通过；关键限制保留、工作完成，不以 Agent 的自述判成功 |

另做恢复、取消、归档缺失、截断工具参数不执行等确定性回归，单独报告可靠性，不混进模型任务成功率。

**6. 压力必须真实且分层报告**

生产设置作为主实验：当前软阈值 300,000 字符、硬阈值 600,000 字符；已配置的模型窗口还会按估算输入加输出预留的 80% 提前触发。实际阈值、模型窗口和预算估算方法必须写入 manifest。

测试集预先划分：低压力任务、接近窗口任务、预算受限长任务。划分依据为冻结输入或独立试跑数据，不能看到 D 成功的题才把它挑进“长任务子集”。同时报告各层、总体、实际清理/摘要触发次数及覆盖率；未触发的题仍保留在所属总体结果中。

可以用较低阈值调试机制，但要给 A/D 相同阈值并单列为应力测试。若 A 在共同硬预算下失败、D 完成，这是“相同预算下的完成能力提升”；应与“两组都可运行时的效率差异”分开解释，不得只靠人为压小窗口制造普遍提升。

**7. 固定这些条件，避免把外部变化当成压缩效果**

- 同一执行框架源码快照、目标代码快照、任务输入及隐藏验收；快照覆盖实际使用的未提交和未跟踪源码，只有 git SHA 不够。
- 同一主模型版本、供应商、摘要模型、system prompt、工具 schema、采样参数、输出上限、重试上限、墙钟上限及任务资源上限。API 不支持固定 seed 时如实记录，不宣称确定性。
- 每 trial 新工作区、新 SQLite、新 archive/tool-results；关闭自动记忆积累和无关 Skills/MCP/委派，防止上一题影响下一题。
- A/B 成对、随机平衡先后，顺序运行起步，记录时段、限流、网络失败及缓存用量。无法强制清空供应商缓存时不标注“冷缓存”。
- 使用同一工具集合。自动压力策略评测可以统一禁用手动 compact；若保留，则两组配置一致并记录手动触发。
- 验收器在 Agent 修改范围之外；允许不同正确实现，只测试任务行为和约束，不要求与参考补丁逐字相同。
- 时间、次数等硬上限需可执行；费用上限如果依赖响应后 usage，只能在调用间停止，必须预留单次请求最大可能开销，不声称能在流中精确按金额截断。

**8. 指标以任务为单位，压缩率只作诊断**

| 指标 | 计算与口径 |
|---|---|
| 任务成功率 | 全部必需行为和回归验收通过的有效尝试数 / 全部有效尝试数；超时、预算耗尽、模型失败不得随意删除 |
| 关键约束违反率 | 如旧格式回流、丢兼容接口、重复一次性副作用；逐项保留判定，再给任务级失败情况 |
| 每次任务 Token / 费用 | 主模型、摘要模型、重试及后续回读引发的全部调用；保存供应商原始 usage 和标准化结果 |
| 每成功任务成本 | 所有有效尝试总费用（含失败）/ 成功数；成功数为 0 时未定义 |
| 完成耗时 | 同一计时边界覆盖 Agent、工具、摘要、回读与恢复；环境准备、验收耗时单列；报告中位数和逐任务分布 |
| 容量与触发 | 最终发送请求大小、provider prompt tokens、投影清除量、摘要尝试/成功/无收益拒绝次数、预算阻断次数 |

费用按经过确认的实际供应商和模型单价计算，区分未缓存输入、缓存读、缓存写、输出；确认字段是否互斥，不能对兼容 API 的字段盲目相加。保存价格来源与日期。费用不完整时报告已知用量和缺失次数，不输出精确降本百分比。

当前 5% 净缩短判断只针对候选主请求大小，还用了估算 Token 的下降约束；它不计算本次摘要费用，也不能保证整项任务省钱。需要测后续真正少花的开销，是否大于摘要、回读和额外执行的开销。

“请求缩短 60%”和“任务总费用下降 60%”是两回事。输入/输出 Token 价格可能不同，缓存命中也可能改变结论。不能用字符数换算真实节省费用。

两组都成功的题可额外报告配对耗时、成本，但必须同时给全任务结果，避免把失败样本筛掉制造好看数据。对超时要标明截止值/删失，不把失败前快速退出当作“完成更快”。样本很少时不主张可靠 P95。

重复工具调用只作诊断：同路径、同参数且文件版本未变的重复读取，与正常验证、增量定位不同；不能把所有同名工具调用都当浪费。

**9. 从小试跑到可用于简历的结果**

1. 免费接线检查：修复第 2 节缺口；脚本客户端覆盖 A/B/C/D、强制摘要、205 条以上历史录制、异常和超时留证。验证 seed 必须失败、参考实现必须通过、空补丁不能蒙混过关。
2. 小规模真实试跑：选择 4 个开发题（含短任务、自然长任务、固定历史续做），A/D 各重复 2 次，共 16 次任务尝试。目的为验证触发、验收和费用规模；不是最终能力结论。
3. 根据试跑费用与耗时确定总预算，最多调整一次策略/限额，然后冻结。为短任务和长任务选合理、组间相同的预算，不让一组无限续跑。
4. 正式主实验可从 24 个未参与调参的任务起步，每题 A/D 各 3 次，共 144 次任务尝试。固定历史续做和端到端任务分表；同一题的 3 次不等于 3 个独立任务。
5. 在事先选定的 8 个代表题补 B/C，各 3 次，再增加 48 次尝试；沿用主实验中这些题的 A/D 数据形成组件对照。不要只选 D 胜出的题。
6. 保留全部失败，复查验收误判；按题聚合配对成本差和成功率差，再以任务为抽样单位给 bootstrap 区间。任务数与重复数是起步方案，不保证统计功效；区间宽就说尚不确定，不能用“不显著”证明质量不下降。

正式预算估算：按试跑各任务类别的实际平均成本 × 计划尝试数，再预留波动空间；不要用一个短 C01 的费用估全部长任务。一次任务尝试会调用模型多次，144 次任务尝试不是 144 次 API 请求。

预先写下质量允许退化幅度和业务理由（示例可设 2 个百分点，但需要足够样本支持）。若要主张质量不劣，配对区间的下界应排除超过该幅度的损失。样本不够时只能说“本样本观察到的成功率为 a/n 与 b/n”，不能说“无损压缩已证明”。

fixture、runner、grader 自身故障记 invalid，保留原因和次数；按预先规则修复后重跑双方相关样本。供应商错误、网络超时、恢复耗尽、模型输出错误、正常预算耗尽按规则计失败，不能随意改为 invalid。若预先约定排除整批外部服务事故，双方成对处理并仍保留次数、实际费用和含事故的总体结果。失败不能挑着重跑直到成功。

**10. 每个结论都能点回原始证据**

每 trial 保留：task/fixture/profile/engine 的哈希、模型与非敏感配置、初始历史及状态、公开请求/响应、逐调用 usage 与 call_id、事件、压缩前后请求度量、归档、文件补丁、独立验收、错误、墙钟时间和价格版本。先脱敏，不能为了留证公开密钥或私人任务材料。

在现有 evidence 目录上增加实验计划与汇总即可：

```text
experiment-plan.json          # 题目、分组、预算、顺序、重复、验收规则
task-id/variant/trial-id/     # 复用已有证据目录结构
per-trial.csv                # 一行一次尝试，含失败与完整性标记
per-task.csv                 # 按题的配对结果，不把每轮请求当独立样本
report.md                    # 总体、分层、区间、失败案例与适用范围
```

推荐三张图：逐请求输入量轨迹并标出摘要与回读；按题的总费用配对图；质量与成本的组件对照图。不同组调用轮数不同时保留各自轨迹，不硬对齐为同一个“第 N 步任务状态”。另外选一个成功案例和一个退化案例，以可见请求、工具行为、文件产物和测试解释原因。

**11. 简历与面试叙事模板**

完整工程论证链是“问题证据 → 可验证假设 → 方案取舍 → 对照实验 → 结果 → 边界与改进”。用外部可核验的行为和产物解释决策；模型生成的大段推理文本不能替代实验依据。

完成实验并有对应证据后可用的项目叙述模板，当前不应写成已完成成绩：

> 长任务中工具输出不断累积，带来重复输入开销和预算耗尽风险。我保留可恢复的已接收历史，按当前请求压力先清理工具冗余，再做语义摘要，并保护近期内容与用户约束。为判断额外复杂度是否值得，构建独立验收的任务集，固定模型与资源上限，比较基础保护、单独清理、单独摘要和组合策略，同时统计摘要与失败开销。实验显示哪些任务获益、哪些不值得压缩，据此确定默认策略。

有数据后填写，以下括号不是已经取得的成绩：

> 设计并实现可恢复的上下文压缩机制；在 [N] 个未参与调参的 [自建/真实来源] 任务、每配置 [R] 次试验中，相比基础保护基线，任务成功率由 [a/n] 到 [b/n]，每成功任务成本下降 [X%]（含摘要与失败开销）；[明确的长任务范围] 的预算耗尽率由 [c/n] 到 [d/n]，通过独立验收、逐调用日志和源码快照支持复现。

如果只看到成本下降且成功率观察值相同，就写观察值和区间；如果只有长任务获益，就限定长任务；如果 B 与 D 基本相同，写清采用更简单策略的取舍。不要填未测的百分比，不把自建题结果称为 SWE-bench 成绩，不把工程回归测试通过率当模型任务成功率。

面试追问应有明确回答：为何需要摘要而不只保留最近 N 轮（组件/替代方案对照）；为何确定是你的机制起效（冻结同代码同模型只切配置）；如何防遗忘（行为约束验收与失败案例）；成本有没有漏算（全部调用及缓存口径）；结果能推广多远（任务来源、范围、样本和区间）；为什么不用更简单方案（B/C/D 的实际差异）。如果最近 N 轮尚未实测，应诚实说明，不能把四组开关实验说成已经比较过所有替代方案。
