**防循环与运行预算方案（设计稿）**

日期：2026-09-23。本页保留实施前的设计依据；当前已实现的行为、默认参数与限制以 [运行说明](loop-guard.md) 为准。数值是初始可配置值，不是经过真实任务评测得到的最优阈值。

**1. 决策与实施顺序**

建议现在加入独立的运行时防循环机制，再调整上下文压缩策略。两项工作通过工具事实、请求提醒和 checkpoint 三个小接口衔接，不把防循环算法放进 ContextManager。

压缩解决模型能看到多少历史；防循环解决执行是否继续。压缩效果差可能增加重复行为，但不能让摘要内容决定是否停机。检测器使用工具执行边界上的事实，不扫描压缩后的 messages，也不要求摘要模型保留精确计数。

当前 `ContextManager.project_messages()` 已将 canonical 历史与模型输入视图区分开，适合这个顺序。后续更改摘要提示词、压缩阈值、保留窗口和工具输出投影，不应修改检测器。若同时重做 Agent 调度或 checkpoint 格式，需要迁移防循环状态，但不必重写检测算法。

**2. 已确认的现状**

- `Agent._run()` 默认最多 50 轮；默认子 Agent 为 30 轮，子 Agent 不能继续创建子 Agent。
- `_execute_tools()` 按工具名、参数、完整错误文本计算连续失败指纹，只在第 2 次追加提醒；成功调用清零，没有强制终止。
- 50 是外层循环轮数，不是工具次数或实际模型请求数。恢复重试、摘要和子 Agent 另有调用。
- 重复调用的离线模拟中，相同成功、相同失败、交替失败均运行到第 50 轮；每轮 3 个相同请求实际执行 150 次。
- 工具结果已具有结构化 `status` / `exit_code`，生产端截断和请求投影发生在后续阶段。
- Web 调度器、父 Agent 和 Team Supervisor 按特定 `stop_reason` 前缀识别失败。增加停止原因时必须同步接入。
- 目前重复失败计数保存在 Agent 实例字段中，不随 checkpoint 保存。

**3. 三层控制**

| 层次 | 解决的问题 | 初始策略 |
| --- | --- | --- |
| 重复失败 | 已得到相同错误仍原样重试 | 第 2 次警告；第 3 次仍相同时，在满足下述证据条件后阻止第 4 次同样尝试 |
| 重复成功／短周期循环 | 一直查同一信息或在几步之间打转 | 初期以警告、记录为主；有可靠状态证据的确定性工具才允许自动停止 |
| 整次执行预算 | 检测不到的循环、批量调用和子任务放大消耗 | 保留轮数上限，增加根任务共享的工具请求预算；模型请求、Token、时间预算分阶段加入 |

强制停止重复失败需要高可信证据：相同参数、相同错误类别或原文、相关前提未变，而且不是工具声明的暂时性故障、正常等待或结果未知。没有状态证据的 Shell／MCP 错误默认仅警告，由总预算兜底。权限拒绝按权限状态版本判断，不能因为模型声称“已经解决”就清零。

警告后至少给模型一次看到提醒并调整方案的机会。同一个 assistant 响应里的批量重复可以积累证据，但不能被解释成模型已经忽略提醒；硬预算和权限限制始终生效。对有副作用的调用不做自动去重、缓存成功或透明重试。

**4. 检测器的数据与证据**

建议新增 `codeagent/runtime/loop_guard.py`，包含 `LoopGuardConfig`、`LoopGuardState` 和 `LoopGuard`；共享预算放在独立的 `RunBudget`。第一版不引入另一个模型来判断“是否有进展”。

每个 Agent 保存最近 20 次工具观察记录，数量和预览长度有上限：

```text
observation_seq, response_seq, agent_id, tool_name
call_fingerprint, result_fingerprint, status, exit_code
resource_key, resource_version, evidence_kind
warning_id, warning_seen_at_response, short_preview
```

- 调用指纹使用工具名和稳定 JSON 参数；对象键排序，列表顺序和字符串原样保留。忽略协议调用 ID，不随意重写 shell 命令、参数大小写或分页位置。
- 结果指纹在 `normalize_tool_output()` 后、追加提醒和 `finalize_tool_results()` 前生成，基于工具实际返回的状态、错误信息和可用原文。上游已截断的内容标记为不完整证据。
- 不使用面向 UI 的截断或脱敏事件作为权威检测输入。事件只用于展示和回放，检测在同步执行边界完成。
- 第一期使用精确指纹。只有工具适配器明确标注的时间戳、耗时等非语义字段才可归一化，避免把不同错误误合并。
- `resource_version` 必须来自可验证事实，例如文件内容摘要、任务状态版本或权限版本。目录搜索若不能廉价取得可靠范围版本，降级为警告。
- 成功返回、TODO 打勾、模型说“完成”、消息增长、Token 增长和压缩成功，都不能单独证明任务有进展。
- 读文件后修改了该文件，再读同一范围属于合法操作。依赖状态未知或变化时解除该资源的强制阻断资格，不能继续按旧版本预测结果。

对已声明确定性的只读工具，连续相同调用和相同结果第 3 次警告；在资源版本仍相同且警告已被模型看到的情况下，可阻止第 6 次调用。普通调查、不同文件、不同页码、新结果和合法的修改后验证均不应触发此规则。

短周期检测只检查窗口内长度为 2～4 的精确模式，例如 `A→B→A→B`。完整模式重复 3 次警告，重复 4 次只对所有步骤都有高可信停滞证据的模式停止；其余仅观测。不要因为中间出现一个成功读取就删除失败记录，也不要把每个成功步骤都当作全局进展。

正常轮询通过工具能力声明区分，使用独立的最小查询间隔和等待期限；`ask_user`、审批等待采用既有等待语义。未知工具不能自行通过返回文本宣称自己属于例外。`compact` 的请求确认不算工作进展，反复无收益压缩可记录警告，但不能通过压缩重置执行预算。

**5. 与压缩的接口契约**

| 操作 | 对检测状态的影响 |
| --- | --- |
| 摘要成功、失败或无收益 | 均不清零计数、不重置预算 |
| 工具内容清理、归档、分页回读 | 保留原执行记录；不同分页参数按不同调用识别 |
| summary_revision / history_generation 变化 | 仅作诊断标签，不视为任务进展或新执行 |
| 被压缩的信息确需重新读取 | 允许有限核验，按真实参数、结果和资源版本判断，不能一次重复就停止 |
| 任务 yield / 同一 attempt 恢复 | 恢复原计数、警告和预算 |
| 新的用户执行或新 attempt | 明确创建新作用域；保留上次终止原因供用户理解 |
| 历史回滚／分支 | 根据调度层的显式分支语义创建作用域，不能由压缩器自行重置 |

防循环状态以独立、带版本的 `execution_guard` 对象随 checkpoint 保存，建议先使用现有 metadata，避免塞入 `context.RuntimeState` 的摘要字段。字段包含 `version`、`scope_id`、`agent_id`、最近记录、警告、停止原因和预算快照。Web 与 Team 保存和恢复均要覆盖它，旧 checkpoint 缺失字段时初始化为空。

首次旧格式恢复不从摘要猜测计数。若持续执行恢复遇到未知新版状态，明确报不兼容并暂停，避免静默丢弃预算。根预算由根任务拥有唯一权威状态；子 Agent 的 checkpoint 只保存本地检测状态和根作用域引用，不能以过期子快照覆盖根预算。

活跃警告从 guard 状态生成一条简短的运行时提醒，与当前请求一起送入模型。提醒必须在请求预算测量前加入，并作为可重建的活跃状态保留；不能依赖旧 tool_result 永远不被折叠。接入点可以复用动态 prompt 组装，不能在 `prepare_before_model_call()` 完成硬预算验证后偷偷追加内容。

压缩器只接收普通提醒文本，不读取或修改 guard 计数。更换压缩策略时只需验证“提醒仍可见、计数不变、完整请求计入提醒开销”。

**6. 执行预算与作用域**

第一期保留主循环 50 轮、子 Agent 30 轮的现有默认值；新增建议初值 `max_tool_requests_per_run=200`，覆盖根执行内所有子 Agent。复杂任务可配置更高值，不能把 200 作为所有任务的正确上限。

工具请求在实际调度前消耗一个名额，被权限拒绝的请求也计数，避免反复申请权限不消耗预算。收到的一批请求逐项检查；超过预算的余项补齐“未执行”结果，不再调度。另行统计真正执行数。父 Agent 的 `subagent` 请求和子 Agent 内部请求各占自己的名额，这是不同的真实请求。

后续可增加以下可选预算，先记录基线再启用默认阈值：

- 实际模型请求总数：包括主模型、显式恢复重试、摘要、记忆和子 Agent。预算接到统一客户端边界，不能只在 `_run()` 外层计数；SDK 内部自动重试需显式配置，否则不能声称精确覆盖网络尝试数。
- 累计 Token：复用 usage，但按 `call_id` 去重并纳入各 `call_kind`；缓存输入计入用量不等于按普通输入计费。usage 缺失标为未知，不能按零计。纯事后检查可能超出一个请求，严格预算需要请求前预留且处理并发。
- 活跃执行时间：包含工具执行、模型请求、恢复退避和摘要，排除等待用户与审批。根任务以活跃区间并集计时，避免父子运行重复累加。恢复保存已用时长，不能持久化进程内单调时钟读数。

LoopGuard 每个 Agent 独立，防止两个执行者恰巧读同一文件互相触发。预算在一个根执行范围共享，并发访问需要原子预留。普通子 Agent 的局部循环停止只返回局部失败，允许父 Agent 调整；根预算耗尽必须传播至根执行并阻止继续创建子任务。

Team 需要单独明确根作用域为一次 TeamRun，不能每次 lead 唤醒就重置。跨 worker 的共享预算应由调度／持久化层持有；在该能力完成前，只启用各 attempt 的局部预算，并明确不宣称已有 Team 全局上限。

**7. 停止协议与用户呈现**

建议统一原因：`loop_detected:repeated_failure`、`loop_detected:repeated_result`、`loop_detected:cycle`、`budget_exceeded:tool_requests`；后续预算沿用同一前缀。

停止检查放在下一次模型调用和每次工具调度前；结果返回后更新证据。若一轮包含多个工具，触发停止时保留已执行结果，并为剩余调用补齐明确的未执行结果。沿用 `_execute_tools()` 的配对和清理机制，不留下孤立 `tool_use`，不把已开始但结果未知的操作写成“未执行”。

不要使用会被 ToolRegistry 转成普通错误、又让模型继续调用的异常路径。由 Agent 返回明确终态；工具调用、上下文压缩和恢复层不能吞掉根预算终止信号。停止后使用确定性文本报告原因，不为了总结再启动一次不受预算约束的模型或自动记忆维护调用。

增加 `agent.loop_warning`、`agent.loop_stopped`、`agent.budget_exceeded` 事件，包含原因、次数、阈值和截断预览。详细参数和完整输出沿用原有受控日志，不重复暴露敏感内容。

- Web：第一版复用 `failed` 存储状态，界面显示“检测到重复操作，已停止”及相关证据；不能落到 `completed`。
- CLI：显示具体停止原因和已完成部分，不只返回空文本。
- 子 Agent：返回结构化或明确可识别的局部失败信息，父 Agent 不应把它当成功交付。
- Team：暂停对应 attempt 并记录原因；禁止 Supervisor 因自动恢复立即重新运行同一个已阻断 attempt。
- 用户明确要求重试时创建新执行作用域并保留前次原因。刷新、重连、压缩和自动恢复都不等于用户重试。

集中维护终态分类帮助函数，接入 `web/scheduler.py`、`Agent._spawn_subagent()` 和 `runtime/background.py`，避免各处遗漏新前缀。第一版无需新增数据库状态枚举。

**8. 分阶段落地与验收**

阶段 A（现在）：独立 guard、精确重复失败警告和有限的高可信阻断、根工具预算（普通子 Agent）、checkpoint 状态、CLI/Web/子 Agent/Team 局部终态接入。未知 Shell/MCP、重复成功和周期模式先记录观测。替换现有重复失败提醒，避免两套计数并存。

阶段 B（修改压缩策略时）：保持三个接口契约，比较压缩前后重复行为；追加“压缩发生在第 2、3 次重复之间”的回归，不重新实现检测器。改善摘要事实保留能降低循环发生率，guard 仍负责最终限制。

阶段 C（有回放数据后）：为常用工具补可靠状态版本，逐步开启重复成功／周期模式停止，调整阈值，再加入跨 TeamRun 预算、模型请求及 Token／时间预算。精确匹配识别不了参数改写等语义循环，这是明确边界，由总预算兜底。

必须验收的行为：

1. 精确失败在阈值内停止；警告至少被模型看到一次；成功插入不能无条件洗掉旧失败证据。
2. 不同文件、不同页码、修复后重试、正常轮询及人工等待不被误杀。
3. 批量调用中途停止，已执行和未执行结果正确配对；未知副作用保持未知。
4. 压缩、清理、摘要失败、来源历史版本变化均不自动重置作用域和预算。
5. Web/Team checkpoint 恢复保留相同 attempt 的计数；旧格式兼容；新执行不继承旧阻断。
6. 子 Agent 局部失败不伪装成功；根预算无法通过重复派生子 Agent 绕过；并发预留不能超发。
7. UI、CLI、Supervisor 对同一终态解释一致，且不会自动恢复成新的无效循环。
8. 检测记录有界；相同请求和结果无论是否经过上下文投影，都得到相同检测结论。

对压缩策略的效果评测应固定 guard 配置，对比完成率、重复调用率、误停率、总用量及延迟。主动停止降低 Token 不等于完成质量改善；循环与压缩事件相关也不等于已证明压缩导致循环。
