# 上下文评测：从打开终端到读懂结果

这份说明按执行顺序写。你不需要先理解评测代码，一次复制一条命令，等它结束，再看结果。

这套题测的是：聊天记录变长后，程序能否正确压缩、找回旧资料、恢复历史，以及真实模型能否继续答对、用了多少 token。固定题不等于真实开发项目的整体成功率。

## 先认识四组，只记住 A 和 D 也够用

| 组 | 程序做什么 | 用来回答什么 |
|---|---|---|
| A | 不做滚动摘要、不清理旧工具结果 | 原始历史直接交给模型，作为对照 |
| B | 只缩短可清理的旧工具结果 | 工具结果清理本身有没有用 |
| C | 只做滚动摘要 | 摘要本身有没有用 |
| D | 两种机制都开 | 当前完整策略有没有用 |

四组都保留基础的单条输出限制、归档及硬预算保护，所以 A 不是关闭所有保护。S04 的入站归档四组都会用到。

固定历史评测现在默认不设置“每场累计 token 上限”，A/B/C/D 一样；之前隐含的 30 万 token 上限已取消。这样不会因为多次请求累计用量超过 30 万，就在答案返回时中断。累计 token 仍照常记录并计算费用。

这不改变触发摘要的字符阈值，也不改变单次输出长度。请求次数、迭代次数和超时限制仍然生效。报告开头会显示“每场累计 token 预算：不设上限”，每场的 `manifest.json` 和 `effective-loop-guard.json` 会记录 `max_total_tokens: 0`。这项默认值只改了固定历史评测，日常 Web/CLI 的默认设置不变。

继续执行下面的 `step` 命令即可使用新设置。若需要专门对比旧的 30 万预算，用 `run` 命令显式指定（会调用真实模型）：

```powershell
python -m evals.context_suite run --mode live --scale stress --cases S03 S04 --variants A D --max-iterations 12 --max-api-calls 16 --max-total-tokens 300000
```

把最后的 `300000` 换成 `0` 就取消累计 token 上限。每次运行都会生成新实验目录；保留之前的结果，不把不同预算的试验混成同一批收益统计。

如果只想知道“摘要本身有没有贡献”，看 A/C、B/D；A/D 比较的是完整策略，不能把全部收益都归给摘要。

## 0. 打开对的终端

在 VS Code 打开项目，点击菜单“终端 → 新建终端”。确认使用 PowerShell。复制下面一行，回车：

```powershell
Set-Location D:\new_codeAgent
$env:PYTHONUTF8 = "1"
```

再检查 Python 和脚本能不能启动：

```powershell
python --version
python -m evals.context_suite steps
```

你应该看到 Python 3.11 或更新版本，以及 `01-check` 到 `09-live-ablation` 的步骤清单。

如果出现 `No module named anthropic`、`langsmith` 等缺依赖错误，先切回你以前成功运行评测的 Python 环境。确实没安装时，再执行：

```powershell
python -m pip install -e ".[web]"
```

安装可能联网下载依赖；它不调用模型。`No module named evals` 通常是当前目录不对，先重新执行 `Set-Location`。

## 1. 测试材料在哪里

已经交付的完整材料包里有这些东西：

| 目录 | 你会看到什么 |
|---|---|
| `materials-stress` | 六道题，较短历史、较低触发阈值，便于先试跑 |
| `materials-production` | 相同六道题，更长历史，使用代码默认生产阈值 |
| `lifecycle` | 连续压缩、跨进程恢复、坏切点和摘要失败的规则材料 |
| `manual` | 真实会话逐轮输入、正常停服重启、工具输出回读的操作材料 |
| `campaign-record-template.json` | 实验登记模板；复制到包外再填写 |
| `steps.json` | 下面每个步骤到底跑几场、最多几次请求 |

需要重新生成整套材料时，运行：

```powershell
python -m evals.context_suite prepare-kit
```

只生成文件，不调用模型。终端最后的 `directory` 就是新材料目录。每次生成新目录，不会覆盖旧包。

六道固定题分别是：

| 题号 | 用日常语言解释题目 | 判对要求 |
|---|---|---|
| S01 | 只聊几句，记住语言和接口 | 答对；正常情况下不应摘要 |
| S02 | 看过很多搜索结果，再找入口 | 文件路径、函数名、格式正确；允许重读工作区资料 |
| S03 | 先要求 CSV，后来改成 JSON | 保留最新字段、编码和禁止覆盖要求，不复活旧方案 |
| S04 | 一大段日志，关键错误在中间 | 通过归档回读取得证据，再准确回答；只猜中不算通过 |
| S05 | 部分步骤成功，部分失败，部分没做 | 不虚报全量通过，不重复合成历史中已完成的发布 |
| S06 | 前一阶段完成，后一阶段卡住 | 记住路径、符号、阻塞编号及下一步，不把阻塞说成解决 |

每道题的 `prompt.txt` 是问题，`seed.json` 是原始聊天材料，`gold.json` 是验收答案，`review-template.json` 是人工审阅摘要用的表。自动脚本负责喂历史、检查答案；你不用手工往聊天框粘贴 seed。

**不要把 gold、评分表或整个材料包作为被测 Agent 的工作区。** 自动试验只向它开放独立的 `workspace`。修改展开后的 seed 不会改变自动评测，正式改题要修改 `cases.json`/材料生成器后再生成。

## 2. 免费检查：题目和判分是否正常

```powershell
python -m evals.context_suite step 01-check
```

它会拿正确答案、错误答案、缺字段答案检查评分器。最后看到 `"valid": true`，说明这些检查通过了。

如果是 false，先看输出目录的 `result.json`，不要继续真实模型测试。它测的是“老师会不会判卷”，不测模型能力。

## 3. 免费检查：程序规则有没有出错

```powershell
python -m evals.context_suite step 02-rules
```

这一步检查：

- 水位是否计入完整请求；该拦的超限请求是否被拦住。
- 切点是否落在合法位置；工具调用和工具结果是否保持配对。
- 老工具结果能否缩短，同时保留原始历史。
- 超长工具输出能否归档和按页读取，中文长行是否丢字。
- 摘要失败时是否保留旧历史，避免错误推进切点。
- 多次摘要、序列化恢复、无效旧状态的处理。
- token 统计、调用上限、评分器和报告本身。

结束后打开输出目录的 `report.md`。所有测试文件组应通过；如果有跳过，去对应日志看原因，跳过不等于通过。最后的 `valid` 必须是 true。

这一步的摘要来自固定响应，不会用真实模型。它证明程序规则，不证明模型会写出好摘要。

## 4. 免费彩排：把六道题完整跑一遍

```powershell
python -m evals.context_suite step 03-rehearsal
```

共六题 × 四组 = **24 场离线试验**。终端会依次显示 `1/24`、`2/24` 等进度。执行顺序被固定种子打散，第一场不一定是 A，这属于正常情况。

结束后打开本次目录的 `report.md`，应看到 `offline`、24 场通过。用量不可用也正常，因为答案由脚本提供。

**离线的 24/24 不要写成模型成绩，也不要拿离线 token 计算节省。** 它相当于考试前检查试卷、监考和判分流程能不能走通。

## 5. 免费检查：连续压缩及重启后还能不能接上

```powershell
python -m evals.context_suite step 04-recovery
```

这一步单独生成恢复证据和 `report.md`，检查多次摘要、保存 SQLite、退出写入进程、新 Python 进程读取并继续，以及失败或历史变化时是否拒绝错误切点。

看到所有规则通过后，再继续。它使用固定摘要响应；这里的进程恢复是正常保存后的恢复，不等于运行中强制杀 Web 服务，更不等于已经验证真实模型的长期记忆质量。真实 Web 重启放在第 12 节。

## 6. 开始花费模型用量之前，确认三件事

前五节无需模型 Key。从下一节 `05-live-smoke` 开始才会请求真实模型。

1. 继续使用你之前已经成功调用模型的 `.env`：`MODEL_ID`、`API_KEY`/`ANTHROPIC_API_KEY`、`BASE_URL`，以及已有摘要模型配置。不用创建两个 Key。
2. 一轮正式比较期间，保持主模型、摘要模型、代码、阈值和调用上限不变。若修改过，就把后续结果登记为新版本，保留旧失败结果。
3. 每个步骤只在你手动输入对应命令后开始，没有“一键自动跑完全部收费实验”。先看小批报告，再决定是否扩大。

随时可以先预览某一步：

```powershell
python -m evals.context_suite step 06-live-repeat --preview
```

`--preview` 只显示参数，不调用模型。正式运行时去掉它。

脚本限制的是请求次数和时间，不是人民币金额。每场默认最多 16 次 SDK 请求、12 轮、180 秒；主模型输出上限 2,048 token，摘要使用当前真实上下文策略的输出设置。摘要和恢复重试都计入 16 次。返回 `max_tokens` 表示这次输出被截断，不能因为有 usage 就当作摘要成功。

## 7. 真实小批：先跑四场

```powershell
python -m evals.context_suite step 05-live-smoke
```

内容：S03、S04 × A/D × 各一次 = **4 场**，真实请求最多 **64 次**。这只是上限，通常不会用满。

结果目录一般形如 `eval-results/时间-context-live-stress-编号`。末尾打印 `directory`，在 VS Code 左侧找到它，点开 `report.md`，可以按 Ctrl+Shift+V 看 Markdown 预览。

重点看：

- S03 的 D 是否答对，摘要成功次数是否至少一次，首个主请求是否比 A 短。
- S04 是否答对并回读到证据。
- 用量是否完整，是否出现摘要截断、调用次数用完、超时。

有失败先查原因，先不要进入大批。S03 摘要失败但最终答对，只说明回退路径可用，不能当作摘要成功。S04 可能使用多次摘要或回读，不能拿 S03 的调用次数要求它。

## 8. 重复五次：看 S03 是否稳定

```powershell
python -m evals.context_suite step 06-live-repeat
```

内容：S03 × A/D × 五次 = **10 场**，真实请求最多 **160 次**。

检查报告中 A、D 分别通过几次，D 摘要成功几次。查看每对 A/D 的 token 差异，不要只挑节省最多的一次。

这个结果测的是“同一道题换几次生成仍然稳定吗”。它仍是一道题的重复，不是五道新题。

建议先把“D 五次都成功产生摘要、五次都答对”作为进入下一步的试运行目标。没达到就如实保留失败，定位问题后另跑新版本；五次全过也不代表永远不会失败。

## 9. 扩大题目：六道题各重复三次

```powershell
python -m evals.context_suite step 07-live-cases
```

内容：六题 × A/D × 三次 = **36 场**，真实请求最多 **576 次**。

这一轮一定要按题看，不能只看总通过率。S01 不需要压缩；S02 可能靠工具结果清理就降到水位以下；S03/S05/S06 重点看摘要；S04 看归档回读。

建议检查：D 是否丢最新要求、是否虚报成功、是否损坏精确路径或编号。如果 D 比 A 少通过，先说明正确性退化，不能只用 token 更少来称赞策略。

本包的 `stress` 表示较低触发阈值，不表示并发压力测试，也不是生产长历史规模。

## 10. 默认生产阈值下再试一次

```powershell
python -m evals.context_suite step 08-live-production
```

内容：六题 × A/D × 一次 = **12 场**，真实请求最多 **192 次**。材料比前面长，单次请求可能更贵，也可能超过所用模型的上下文容量。次数更少不代表费用更少。

它不降低代码的默认压缩阈值（当前默认约 30 万字符；stress 约 4 万字符）。先确认供应商支持该请求长度。遇到明确的模型窗口超限，记录下来并设置真实模型窗口后新开一批，不要把超限归因于模型答错。

想使用明确的模型窗口时，可使用原始 run 命令的 `--context-window-tokens` 和 `--summary-context-window-tokens`；不要凭空填写模型窗口数字。窗口为 0 表示未配置 token 窗口，并不是无限上下文。

本步一次只是生产规模试跑；准备正式总结时可以在参数不变的情况下再运行两次，并把三批都登记。不要把不同代码快照或不同模型结果直接合成同一个实验。

## 12. 真人操作：三次摘要和 Web 服务重启

自动固定历史题每场只有一次续答，不能替代真正连续聊天。打开材料包 `manual/README.md`，按里面的案例操作。

- M01：复制第一轮问题，等正常结束；发压缩指令，确认确实出现成功压缩事件；再发下一轮。连续做三次摘要，最后问有效约束。
- M02：在独立端口、独立数据目录启动测试服务；正常完成并保存回合后停止，再用同一目录启动，打开原会话继续。
- M03：从真实文件工具读取长输出，再根据工具返回的归档位置回读中间的证据。

每个案例都有完整逐轮 `prompt.txt`、隔离工作区、期望答案、证据导出和结果填写模板。照案例自己的 `操作.md` 执行，不要把期望答案一起粘贴给模型。

手工案例要从材料包准备到独立执行目录，不要让 Agent 使用整个项目或整个材料包作为工作区。启动脚本与导出脚本的具体用法见 manual 的说明。

这是人工真实模型测试，运行会产生用量。生成这些文件不代表已通过。M01 的手动 compact 主要验证多轮记忆传递，不能用于证明自动水位判断；M02 正常停服不等于工具执行中断后的副作用幂等性。

## 13. 怎样读 token 表，避免算错

新报告直接展示 token 表，并区分主调用和摘要调用。每组所有试验都计入，包括失败试验里已经产生的用量。

报告现在还会展示人民币费用估算，与总 token 放在同一张总览表中。按你提供的截图，空闲单价为每百万 token：未命中输入 1 元、命中缓存 0.02 元、输出 4 元；高峰分别为 2 元、0.04 元、8 元。主模型和摘要暂按同一价格表分别计算。

两列分别是假设所有请求都按空闲或高峰价格计算，不会根据文件生成时间自动猜计费时段。模型、平台及价格生效日期还未核实，所以这是条件估算，不是实际账单。费用表包含摘要开销和失败试验；缺失用量不按零处理。截图没有缓存创建单价，如果出现非零的缓存创建用量，费用会显示未知。

价格配置在 `evals/context_suite/pricing.json`。`main` 为主模型，`context_summary` 为摘要模型，二者可以分别填写价格。所有单价都是人民币/百万 token；未提供的价格保留 null，不要填 0。每份报告的 `result.json.cost_estimates.pricing` 保存本次所用价格和文件哈希，方便以后核对。修改价格后对旧实验运行 regrade，会在新目录生成新估算，不改旧报告。

本项目 Messages 格式的总量口径是：普通输入 + 缓存创建输入 + 缓存读取输入 + 输出。不要套用其他接口里 `prompt_tokens` 已含缓存的算法重复加算。兼容服务的字段语义仍需与实际供应商口径核对。

先看下面三件事：

1. 两组是否都完成了同样数量的试验？是否使用相同题目、模型和历史？
2. 用量是否完整？缺失显示不可用，不能填 0；offline 不计算真实节省。
3. D 的主模型加摘要总量是多少？不能只看摘要后的第一条请求。

相同试验数且用量完整时：

```text
减少比例 = (A 总 token - D 总 token) / A 总 token × 100%
```

例如你已有那次 A 是 212,537，D 是 106,015，则总量减少约 50.1%。在上述价格假设下，空闲费用约为 A=0.04832044 元、D=0.05353224 元，D 的费用反而增加约 10.8%。因为主要减少的是便宜的缓存输入，同时增加了普通输入和摘要输出。这个单次结果不能推算整个项目的平均收益。原 `cost` 和 `actual_billed_cny` 保持 null，估算单独保存在 `cost_estimates`，等待账单核验。

报告中总量较低，但 D 没写完答案，不能叫“同等效果下节省”。正确性和消耗必须一起看。缺 usage 的批次不能计算完整节省，已知部分仍保留以供排查。

## 14. 给旧报告补 token 表，不再调用模型

对你之前那次成功实验直接运行：

```powershell
python -m evals.context_suite regrade eval-results/20260923T135008Z-context-live-stress-bd26d4fd
```

程序先检查原始证据有没有被改动，再在新目录生成报告，原目录不变。这会按当前评分和报告代码重算，必须注明“对旧证据重新统计”，不能当作又跑了一次实验。

想处理其他批次，就把命令最后的目录换成那次真实输出目录。不要输入带尖括号的占位路径，也不要指向 `report.md` 文件本身。

## 15. 如何保存证据和写结论

每次结束，把终端显示的结果目录记到从 `campaign-record-template.json` 复制出来的登记表中。保留成功和失败，不删掉“不好看”的那次。

检查文件有没有在运行后被改动：

```powershell
python -m evals.context_suite verify eval-results/20260923T135008Z-context-live-stress-bd26d4fd
```

换成你要检查的结果目录即可。`valid: true` 表示封存后文件一致，不代表模型成绩合格。

实验目录里：

- `report.md`：先看它，给人读的总表。
- `result.json`：逐题评分、用量和失败原因。
- `trial-.../workspace/answer.json`：模型实际交的答案。
- `trial-.../model-responses.jsonl`：每次返回的内容及原始 usage。
- `trial-.../model-requests.jsonl`：每次实际发出的公开请求。
- `trial-.../final-state.json`：最后摘要和切点。
- `trial-.../stderr.txt`：异常和发送 LangSmith 时的错误。
- `source-manifest.json`：当前代码与本次冻结代码的标识。

每个批次开始时，脚本会把当前代码复制一份，整批用同一份跑。每场自己的文件、数据库和模型客户端互不混用。这个隔离不保证供应商缓存隔离，缓存冷热仍需看返回用量，不能靠换两个 Key 假定独立。

简历可以写“在六类合成固定历史题、多少次对照试验中，A/D 通过率分别为……，包含摘要开销的总 token 用量变化为……”。题数、重复次数、规模和失败结果都要有依据。没有实际验证的项目平均收益、真实费用、真实发布幂等性不要写成已完成。

## 遇到问题时，看这一页

| 看到的现象 | 是什么意思 | 下一步 |
|---|---|---|
| `offline` 全通过但 LangSmith 没记录 | 离线只用脚本，关闭上传 | 想测模型时运行明确的 live 步骤 |
| `usage 完整=True` 但摘要 1/0 | 请求有用量，摘要仍可能不完整 | 看摘要 stop_reason 和失败说明 |
| D 首请求跟 A 一样长 | 可能摘要失败或没有合适切点 | 看摘要成功次数、context 事件，不凭字符数猜原因 |
| 摘要 `max_tokens` | 单次摘要写到输出上限 | 调查摘要长度和提示词；增加整场调用次数不是同一件事 |
| `模型调用次数达到上限` | 16 次机会用完 | 看是否多余回读或重试，先诊断再改变预算 |
| 超时 | 180 秒内没结束 | 看已保存请求、错误和调用次数；失败照样保留 |
| 不允许覆盖材料目录 | 防止把旧证据盖掉 | 不带 `--output` 生成新的唯一目录 |
| Token 数据不可用 | 缺字段、缺响应、离线或数据不匹配 | 保留原记录，不当零用量、不计算节省 |
| 没看到 LangSmith | 可能开关未启用、项目/时间过滤或发送失败 | 看终端 enabled、trial 的 tracing.json 和 stderr.txt |

LangSmith 记录名形如 `eval.context.S03.D.r1`，重复运行会同名，结合 metadata 的 suite/trial 和时间区分。模型调用的 `call_kind` 区分 main 与 context_summary。本地请求和响应是主要完整证据，界面截短不等于本地丢失。
