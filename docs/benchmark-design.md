# CodeAgent 评估系统设计与实施步骤

版本：v1.0，2026-09-05。状态：待实施设计。

入门请先看 [从零开始的操作教程](D:/new_codeAgent/docs/benchmark-walkthrough.md)：按软件、操作位置、可复制的 AI 提示词和验收结果逐步说明。本文保留为技术参考，不作为小白的第一阅读入口。

本文定义要建设的评估系统、实验步骤和验收标准。文中的样本量、配置、目录和命令是建议；除“已核验事实”外，均不表示评估已经执行。所有实验结果先保留为空。

阅读入口：先看第 16 节的 E01–E15 实施清单；做任务时看第 4 节，做运行器和判分器时看第 5–8 节；分析结果时看第 14、17 节；整理简历时看第 18 节。第一轮先完成两个带参考补丁的小任务与假模型闭环，不必一开始准备全部测试集。

## 1. 要回答的问题与实施顺序

你需要证明三类能力：实际任务完成能力、机制正确性，以及引入机制后的收益和代价。每一类使用对应的判分方式。

| 阶段 | 问题 | 最小交付物 | 是否消耗真实模型额度 |
| --- | --- | --- | --- |
| P0-A | 能否自动、重复地评估一个代码任务？ | 任务规范、独立执行器、隐藏判分器、逐次记录 | 前期使用假客户端，最后少量试跑 |
| P0-B | 核心安全、恢复和调度机制是否符合设计？ | 安全测试集、故障矩阵、状态断言报告 | 不需要 |
| P0-C | 同模型下，指定运行时配置是否改善编码任务结果？ | 20 题、2 组、每题每组 3 次的初步报告 | 需要，共 120 次完整 Agent 运行 |
| P1-A | 历史摘要压缩是否值得？ | 长上下文配对实验、成功率与 Token 报告 | 需要，独立预算 |
| P1-B | 多 Agent 何时更快，成本增加多少？ | 固定 DAG 实验及完整 Team 实验 | 需要，独立预算 |
| P2 | Memory、Skill、MCP 的增益和边界是什么？ | 有针对性的独立实验 | 部分需要 |

第一版做到 P0-C 就可以形成一份有依据的项目结果。P1、P2 分批推进，不要求一次性全跑。样本量是个人项目初步评估规模，不是统计效力保证。

## 3. 第一步：固定实验协议和研究版本

### 3.1 写下可检验的假设

先使用中性的研究问题，避免预设必须得到某个提升数字。

- H1：在同一模型和预算下，配置 S1 相比 S0 的任务通过率、耗时和消耗有什么变化？
- H2：在预先构造的长上下文任务上，历史摘要压缩如何影响约束保持和完成率？
- H3：相同 Task DAG 下，1 与 3 个 Teammate 的候选交付耗时和成本如何变化？
- H4：对允许、需审批、拒绝三类请求，运行时能否按协议处置？
- H5：发生不同类型和位置的故障时，运行时能否进入预期状态并避免重复副作用？

### 3.2 保存研究版本

1. 为实验准备一个不再变化的 CodeAgent 源码快照。
2. 可使用已提交的实验版本；若保留未提交状态，额外保存差异补丁、未跟踪源码清单、文件内容哈希和本地运行所需模板。
3. 对相关子模块单独记录版本和差异。未使用的组件标记为 excluded。
4. 记录 Python、Node、SDK、操作系统、Shell、依赖锁文件或完整依赖清单。两个对照组使用相同环境。
5. 生成 `harness_snapshot_hash`，使实验结果关联的是实际执行的代码集合。
6. 冻结 Prompt 模板、工具 Schema、Skill、预置 Memory；保存哈希与实际配置快照。

API Key 等凭证不进入快照。实验目标仓库只获得其基线内容；评估工具源码、隐藏答案和研究仓库的其他资料位于外部。

### 3.3 预先固定处理规则

- 一次 trial 是从干净初态开始，在统一预算内执行到截止点的一次完整尝试。其内部多轮工具调用和允许的重试不产生新 trial。
- 每个任务每组重复 3 次，不从重复运行中挑最好的一次代替全部结果。
- 超时、预算耗尽、补丁无效、未提交候选都保留记录。
- 修改 Prompt 或修复运行时后产生新的 experiment，不覆盖旧结果。
- 开发集可以反复分析；测试集看过结果后再针对性调参，该测试集转为回归集，新结论需新的留出任务验证。
- 分母、超时、人工介入、异常重跑规则在看正式结果前确定。
- 不预设收益合格线。能准确记录负结果也是评估系统验收成功。

产物：`protocol.md`、环境清单、代码快照与实验配置哈希。

验收：另一台符合环境要求的机器能够知道运行的是哪一份代码、哪一种配置、哪一组任务。

## 4. 第二步：建设任务集

### 4.1 首批任务组成

| 集合 | 建议规模 | 内容 | 用法 |
| --- | --- | --- | --- |
| dev | 5 题 | 2 个缺陷修复、2 个小功能、1 个跨文件任务 | 调试 runner、grader、预算与 Prompt |
| coding-v1 | 20 题 | 8 个缺陷修复、8 个功能修改、4 个行为保持重构 | 正式比较 S0 / S1 |
| context-v1 | 8 题起 | 前置约束、长日志、跨文件理解、多阶段进度 | 独立压缩实验 |
| team-v1 | 6 题起 | 2 个分支独立、2 个部分依赖、2 个冲突或串行控制任务 | 独立并行实验 |

前两组优先来自至少 3 个仓库。不要只使用 CodeAgent 自身，否则仓库习惯和开发经验容易影响代表性。跨文件、长上下文等可以作为标签，与主要任务类型分开。

每题标明 `source_kind=historical_issue|self_authored|synthetic`。合成任务不能在简历里全部称为真实开源 issue。仓库授权和依赖安装条件也要可复现。

### 4.2 制作单题的操作步骤

1. 选择一个有明确完成条件的需求；历史 issue 记录原始 URL 和修复前 commit。
2. 在干净环境安装依赖，跑基线回归测试，排除本身损坏、依赖无法获取和不稳定的题目；保留排除原因。
3. 根据需求编写 Agent 可见的 prompt，包含必要的输入输出规则，不泄露实现方案。
4. 编写隐藏验收测试，覆盖正常行为、至少一个边界情况和相关旧行为。
5. 验证初态在目标测试上失败，参考实现通过目标测试及回归测试。历史已有失败需逐项固定名单，不能运行后临时忽略。
6. 保存 allowed scope；如果定位能力本身是考点，给完整仓库范围，避免通过过窄文件名单泄露答案。
7. 冻结任务、测试和环境哈希，再加入对应数据集。

重构题若功能测试在修改前就通过，需要额外结构验收，例如删除指定重复逻辑、保留公开接口、通过独立静态规则。无法客观约束的题目先移出自动主指标，改为人工盲审子集。

### 4.3 单题示例：CLI 错误处理

需求示例：CLI 缺少必填参数时输出错误帮助并返回非零退出码，正常调用仍生成正确结果。

隐藏检查：缺参退出码、错误信息关键要求、合法参数原输出、Unicode 路径、输入不存在时的行为。判分按语义断言，不强制所有提示文本逐字匹配。

参考修复用于验证 grader，不放入执行环境。Agent 可以添加自己的测试，但最终判分必须来自外部固定测试。

### 4.4 公共任务数据与私有判分数据

下面是拟定的公共元数据示例，所有占位值必须在冻结时替换：

```json
{
  "schema_version": 1,
  "task_id": "cli-argument-001",
  "split": "dev",
  "source_kind": "self_authored",
  "repository_id": "fixture-cli",
  "base_commit": "<full-commit-sha>",
  "prompt_file": "prompts/cli-argument-001.md",
  "category": "bugfix",
  "tags": ["cli", "regression"],
  "environment_id": "fixture-cli-env-v1",
  "allowed_write_scopes": ["src/**", "tests/**"],
  "network_policy": "model_endpoint_only",
  "grader_id": "cli-argument-001-grader-v1",
  "memory_snapshot_id": null
}
```

完整 manifest 由 controller 持有；只把当前任务真正需要的描述和约束交给 Agent。`grader_id` 是标识符，不是给 Agent 可读取的隐藏测试路径。私有 manifest 单独保存目标断言、回归测试命令、测试哈希、参考补丁和结构评分规则。

目标仓库的 Git 对象只包含被允许的基线历史，不能保留可检索到未来答案的修复分支、远端 refs 或隐藏测试提交。Memory、Skill 和 MCP 不得包含该题答案。

产物：5 个已验证开发题、20 个待冻结正式题、题目清单及私有 grader。

验收：对每道正式题跑“基线 + 参考实现”校验；应失败和应通过的项目与任务规范一致。仅测试夹具损坏的题目在正式运行前排除。

## 5. 第三步：搭建评测目录与组件

以下目录是拟建结构，不表示这些模块已经存在：

```text
evals/
  __main__.py                 # 提供 validate / run / grade / report 等入口
  schemas.py                  # TaskSpec、Profile、TrialResult
  controller.py               # 枚举 trial、排序、状态持久化
  runner.py                   # 单次 Agent 运行生命周期
  environments.py             # 基线环境、独立工作目录、进程清理
  adapters/
    single.py                 # 复用单 Agent 构造逻辑
    team.py                   # 复用 TeamSupervisor、SQLite 和 Worktree
  instrumentation.py          # 请求、事件、计量、文件快照
  grading.py                  # 外部固定判分
  faults.py                   # 假客户端与故障时间线
  safety.py                   # 三态权限与副作用判分
  metrics.py                  # 只读取记录进行聚合
  report.py                   # 结果表、配对差异、失败清单
  profiles/                  # 不含凭证的实验配置
  datasets/                  # 公共任务清单和说明
  fixtures/                  # 小型合成仓库、预置记忆等
  tests/                     # 评测系统自身的验收测试
```

运行期数据存到独立的 `eval-data/<experiment_id>/<trial_id>/`，不放进被测目标工作区。隐藏 grader 存在 controller 的私有目录，禁止挂载到执行器。

首版直接使用 Python dataclass、JSON/JSONL 和标准库测试即可，复用项目现有 SQLite、事件与 FastAPI 相关依赖。需要结构化测试结果时，可固定使用目标项目已有测试框架的 JUnit/XML 输出或明确的结构化适配器。

组件关系：

```text
Controller 持有任务、配置、私有 grader
  → 初始化 Executor（仅模型调用与目标仓库工具）
  → Runner / SingleAdapter 或 TeamAdapter
  → 冻结 Patch 与事件记录
  → 独立 Grader 应用 Patch 并运行固定验收
  → TrialResult
  → Metrics / Report（无需再次调用模型）
```

Windows 第一阶段可用临时目录和独立子进程完成假客户端测试。正式任意 Shell 执行和隐藏测试隔离建议使用受限容器/独立环境；Worktree 负责代码目录隔离，不承担系统沙箱职责。若使用 Linux 容器，则报告该实验平台，不能顺带声称已验证 Windows Shell 安全。

产物：能以假客户端完成一题的最小流水线。

验收：不需要 API Key，成功、验收失败和超时各跑一题，都能生成记录并释放所属进程。

## 6. 第四步：定义一次运行的状态和结果

### 6.1 运行状态

```text
prepared → running → collecting → grading → finalized
```

`finalized` 表示记录已封存，功能判分与运行状态分开保存：

- `functional_pass`：隐藏目标断言、指定回归和结构断言是否通过。
- `policy_pass`：修改范围、人工干预等是否符合本组协议。
- `budget_pass`：是否在声明预算口径内结束。
- `protocol_valid`：任务、配置与判分证据有效，没有违规人工修复等导致结果无效的问题。
- `success`：以上四项均为 true。只有费用计量缺失而功能证据完整时，可保留功能/任务结果，但费用指标标为不可用；关键判分证据缺失则不能记成功。
- `outcome`：`passed`、`acceptance_failed`、`scope_violation`、`timeout`、`budget_exceeded`、`protocol_incomplete`、`agent_error`、`infra_error`、`cancelled`。

即使超时后的残留补丁通过测试，也不能把超时 trial 计为预算内成功。可以将该补丁功能结果作为附加分析保存。

### 6.2 单次 TrialResult 的建议格式

```json
{
  "schema_version": 1,
  "experiment_id": "coding-v1-exp001",
  "trial_id": "cli-argument-001-S1-r01",
  "task_id": "cli-argument-001",
  "profile_id": "S1",
  "repeat_index": 1,
  "harness_snapshot_hash": "<sha256>",
  "task_hash": "<sha256>",
  "profile_hash": "<sha256>",
  "grader_hash": "<sha256>",
  "model_requested": "<model-id>",
  "model_reported": null,
  "provider_endpoint_id": "<non-secret-id>",
  "seed": null,
  "sampling_settings": {},
  "state": "prepared",
  "outcome": null,
  "functional_pass": null,
  "policy_pass": null,
  "budget_pass": null,
  "protocol_valid": null,
  "success": null,
  "runtime_run_ids": [],
  "team_run_id": null,
  "timing_ms": {},
  "usage": {},
  "human_interventions": [],
  "artifacts": {},
  "failure_reason": null
}
```

状态未定或用量未知使用 `null`，不使用 0。模型不支持 seed 时记录 null；支持 seed 也不承诺跨服务版本完全确定。

### 6.3 每次运行保留的文件

- `config.resolved.json`：解析后的真实配置与软硬预算说明。
- `result.json`：trial 结果与引用。
- `events.jsonl`：全部运行事件，保留唯一事件/调用 ID。
- `model-calls.jsonl`：每次主模型、子 Agent、摘要和 Memory 调用；失败记录同样保留。
- `requests.redacted.jsonl`：必要的实际请求内容及哈希，仅保留接口暴露内容，过滤凭证。
- `transcript.jsonl`：Agent 可观测的消息和工具结果；与 UI 预览截断区分。
- `patch.diff`、`changed-files.json`：变更及新增/删除文件清单。
- `grade.json`、`grade.log`：固定判分结果、测试数量、退出码、耗时。
- `approval-events.jsonl`：审批依据、自动策略决策和真实人工操作。
- `integrity.json`：产物哈希清单。

已有 Web 事件会脱敏并限长，不能保证包含完整原始工具输出。评估新增采集器应在相应观测点保存受限访问的原始证据，并生成用于公开分享的脱敏副本。

## 7. 第五步：实现 Single Runner 与独立 Grader

### 7.1 执行流程

1. Controller 校验任务、profile、环境和预算，把运行计划写入实验 manifest。
2. 在已准备好的基线镜像或快照上创建 Executor；环境构建与依赖安装单独计时。
3. 分配独立 RuntimeDataPaths、SQLite、Conversation、工具状态和日志目录；不加载个人 `.env`、个人 Memory 或旧 checkpoint。
4. 用显式配置构造 `EnvironmentConfig` 和 `WebAgentFactory`，保留真实权限检查。用适配器设置实验策略，避免改造一条脱离产品的循环。
5. 创建每个 trial 独立的 SDK 客户端和观测代理；为本次实验设置 SDK 重试策略。
6. Controller 记录单调时钟起点后交付 prompt；启动外部 watchdog。
7. Agent 正常结束或达到边界后，停止新的调用。超时则先请求协作取消，宽限期后由外部控制器终止该 trial 所属进程树。
8. 确认所属进程已退出，再冻结文件快照、导出补丁与证据，防止冻结后仍有写入。
9. 将候选补丁复制到独立 Grader 环境，恢复基线后只应用候选变更，再注入可信隐藏测试。
10. Grader 运行目标断言、固定回归、修改范围和其他预注册检查，生成最终结果。

Linux 可使用 trial 进程组/容器生命周期；Windows 需使用可跟踪所属子进程的 Job Object 或等效机制。取消一个 Python Future 不能证明底层 Shell 已停止。

### 7.2 补丁与测试可信性

- 不能只执行 `git diff HEAD` 就认为捕获了所有文件：它不会自动包含未跟踪新文件。补丁适配器必须覆盖新增、删除、重命名和需要支持的二进制文件，并用临时仓库 round-trip 验证。
- 只在 trial 所属目录或临时索引操作，不对用户研究工作区执行 reset/clean。
- Agent 生成的测试可作为运行轨迹，但不能替代固定验收。
- Grader 使用自己的固定入口，不能只相信 Agent 修改过的测试配置或打印出来的“通过”。
- Grader 同样会执行不可信候选代码，应在无凭证、无非必要网络、无宿主敏感挂载的隔离环境中运行；可信测试与报告收集逻辑不允许候选进程改写。固定测试发现和插件加载规则，防止候选配置接管判分。判分完成后的隐藏测试和详细结果不回灌给同一正式 trial 的 Agent。
- 验证实际收集的固定测试数量，0 个测试、异常 skip、测试发现被关闭应判无效或失败。
- 预注册可修改文件范围。真正需要改构建配置的任务，应提前定义允许行为，避免临时放宽规则。
- 本轮被测任务默认断网，仅保留模型服务连接；依赖提前准备。需要联网的任务归入独立类别并记录访问规则。

### 7.3 评测系统自身要通过的验收

1. 假 Agent 仅声称“完成”、不修改代码：目标测试失败。
2. 假 Agent 正确修改：所有约束通过。
3. 正确新增文件：补丁重放后文件存在且测试通过。
4. 只修改/删除测试伪造成功：外部 grader 仍判失败。
5. 修改范围外文件：policy 判失败。
6. Agent 抛异常或挂起：记录完整，watchdog 能终止所属进程。
7. 两个重复 trial 之间不共享 Memory、文件、SQLite 或消息历史。
8. 任意 trial 丢失关键计量或判分证据：报告显式标记，不静默当作 0 消耗或成功。

## 8. 第六步：建立可解释的对照组

### 8.1 第一组实验只回答一个问题

问题：在相同模型、基础工具和预算下，长任务治理机制是否改善完成率，代价是什么？

| 配置 | S0：基础循环 | S1：长任务治理 |
|---|---|---|
| 模型、基础 prompt、工具 schema | 相同 | 相同 |
| Bash、读写、编辑、搜索、TODO/TASKS | 开启 | 开启 |
| 权限检查、观测、外部 watchdog | 开启 | 开启 |
| Bash 自身的输出截断 | 保持现有行为 | 保持现有行为 |
| 主动/反应式历史压缩 | 关闭 | 开启 |
| Context 的大输出治理 | 关闭其额外处理 | 开启 |
| 框架级可恢复错误处理 | 关闭 | 开启 |
| SDK 自动重试、模型 fallback | 关闭 | 关闭 |
| Memory、Skill、MCP、普通子 Agent、Team | 关闭 | 关闭 |
| 人工参与代码修复 | 不允许 | 不允许 |

这是“长任务治理组合”的对照，不是“完整框架 vs 无框架”，不能据此把收益归因于其中某一个模块。需要归因时，再增加“仅压缩”“仅恢复”等消融组。先做两组，控制成本。

两个组都移除手动 compact 工具，保持公开工具 schema 一致，避免 S0 通过工具间接开启压缩。保留 TASKS 时，应保持提醒 Hook 配置相同。现有 `mode=off` 不能代表所有输出处理和反应式压缩都已关闭，需补独立开关并写测试。

### 8.2 建议的首轮参数

以下是待试跑校准的实验配置，不是仓库已经支持的 CLI 或环境变量。

```json
{
  "profile_id": "S1",
  "model": "<固定的实际模型标识>",
  "summary_model": "<固定的实际摘要模型标识>",
  "sdk_max_retries": 0,
  "sampling_parameters": {},
  "initial_max_output_tokens": 8000,
  "recovery_max_output_tokens": 16000,
  "max_root_iterations": 50,
  "max_total_logical_model_calls": 80,
  "trial_deadline_seconds": 1200,
  "tool_timeout_seconds": 120,
  "total_token_soft_limit": 200000,
  "framework_retry_limit": 2,
  "continuation_limit": 1,
  "context_char_threshold": 300000,
  "trial_concurrency": 1,
  "approval_policy": "coding-local-v1"
}
```

- `sampling_parameters` 只保存真正发送且受模型支持的参数；没有设置 temperature 或不支持 seed，就如实记录，不写“固定随机种子确保完全复现”。
- 摘要、重试、续写、Team 子运行都算调用和消耗。root 的 `max_iterations` 不是整个 trial 的总调用上限。
- 总 token 限制先作为 soft limit：调用返回后才能拿到真实 usage，最后一个请求可能越界。若要宣称硬预算，需要请求前预留额度、限制并发、限定输出，并说明输入 token 估算误差。
- 固定每请求上限、全局请求数和外部截止时间；触发预算后停止接纳新请求。对在途调用和工具使用同一取消/终止策略。
- 阈值应在开发集定好后冻结。正式集结果不好，不能临时提高某一组预算。
- 采用预定义审批策略：仅自动批准评测沙箱内的低风险开发操作；不自动批准外部发送、工作区外写入等行为。需要人工审批的实验单独报告等待时间和参与次数。

### 8.3 必须先补的最小接口

| 顺序 | 接口改造 | 验收标准 |
|---|---|---|
| I1 | 显式注入 SDK 重试参数与观测代理 | 注入一次 429，能区分一个逻辑调用与实际 HTTP 重试次数；S0 的 SDK 重试确为 0 |
| I2 | 完整关闭框架恢复，并明确耗尽后的终态 | off 不发生异常重试、续写或输出上限提升；达到上限后失败结束，不继续空转 |
| I3 | 拆分主动压缩、反应式压缩、输出治理开关 | 单独开启时只触发对应分支；同时关闭时没有隐式压缩 |
| I4 | trial 级调用账本与预算检查 | 摘要、子 Agent、Lead 后续新 run_id 均计入；相同 call_id 不重复计数 |
| I5 | 在治理前后记录长度和完整 usage | 原始/处理后字符数、压缩原因、缓存字段、usage 缺失原因都有记录 |
| I6 | 记录 Team 候选完成与最终验证时间 | 明确区分候选补丁就绪、机械集成、最终测试完成 |

SDK 的默认重试会影响对照口径，必须显式控制。[Anthropic Python SDK 文档](https://platform.claude.com/docs/en/api/sdks/python)

不得通过替换 `ToolRegistry.with_execution_wrapper()` 覆盖原有 Team 权限门禁；该接口不是自动叠加 wrapper。优先在事件、客户端代理和现有门禁内部加入只读观测点。

## 9. 第七步：先做不消耗真实模型额度的测试

### 9.1 安全策略测试

先编写 100 条不同案例：正常允许 50 条、必须确认 25 条、明确禁止 25 条。这只是建议规模，不是结果，也不是把同一输入重复 100 次。

覆盖正常文件编辑、项目内命令、危险命令变体、绝对/相对路径、`..`、符号链接/Windows junction、工作区外写入、MCP 副作用、失效 lease、冻结候选补丁。按平台划分适用集；不支持的场景标记 skip，不算通过。

每条案例保存工具名、参数、平台、权限上下文、预期决策 `allow/ask/deny`、是否允许实际执行。先固定策略标签，不让模型判断自己是否安全。

分两层执行：

1. 策略单测：用带调用计数器的假 handler，验证被拒绝或尚未确认时 handler 没有执行。
2. 隔离集成测试：在一次性环境创建无价值标记文件，验证文件、进程或模拟服务的实际副作用。危险输入不在宿主机真实执行。

分别统计正确允许、正常操作误拒绝、正常操作多余确认、危险操作执行前拦截、执行后才检测到越界、未发现的越界。不能把“写入发生后 freeze”算作“成功阻止写入”。

当前 Shell、MCP 的写后审计不等于 OS 沙箱。没有独立 OS 隔离时，最多报告策略单测和受控集成结果，不宣称验证了任意命令安全性。

### 9.2 错误恢复与故障注入

先做约 20 条确定性故障序列。每条声明注入点、返回序列、最大尝试次数、预期终态、预期副作用次数。

| 故障类别 | 核心断言 |
|---|---|
| 一次 429/5xx 后成功 | 有界退避后完成，失败尝试也计量 |
| 持续 429/5xx、网络超时 | 耗尽后结束，不无限重试或误报成功 |
| 401、无效参数 | 不对不可恢复错误反复重试 |
| 529 与 fallback | 主实验关闭 fallback；专门用例验证开启行为 |
| 上下文超限 | 有界压缩恢复，保留早期约束 |
| 普通文本输出截断 | 提升上限/续写不突破预设边界 |
| 工具调用被截断 | 不执行畸形参数，不重复产生副作用 |
| 摘要调用失败 | 原始历史未损坏或静默丢弃 |
| 写入完成、结果未持久化 | 标记不确定，不盲目重放非幂等写入 |
| lease 失效、重复认领 | 同一任务至多一个有效 owner，旧 owner 不能提交 |
| checkpoint 后重启、checkpoint 前崩溃 | 按真实持久化粒度恢复或明确中断 |

普通重试单测用 fake clock；进程取消、真实超时保留少量实际计时测试。“可恢复故障最终恢复率”和“全部故障处理符合预期率”分开：不可恢复错误正确失败不是恢复成功。

用唯一操作标记或模拟服务计数核验重复副作用，不能只数日志。当前 checkpoint 不应描述为每工具步自动恢复。

这些测试证明控制逻辑，不直接证明真实 LLM 理解错误反馈的能力；如需测后者，另建少量真实模型实验，单独计费报告。

### 9.3 DAG 与调度不变量

固定 DAG 覆盖独立任务、串行链、扇出/汇合、资源冲突、上游失败、审批、取消、重复消息、运行中重启。

断言依赖未满足不执行、冲突资源不并发写、取消后不接新任务、Future 未结束不提前释放写资源、旧 lease 不能提交、重复 command_id 不重复生效。

已有 100 线程认领测试是同进程竞争测试，不能称为“100 个 LLM Agent 并发稳定运行”。多进程、多连接竞争另测，记录锁等待和失败类型。

本步产物：安全案例级报告、故障序列报告、调度不变量报告。验收：所有差异有证据，未覆盖和不适用项明确列出。

## 10. 第八步：开发集试跑与预算核算

1. 假客户端先通过第 7.3 节全部验收，不调用付费模型。
2. 选 1 条开发任务，S0/S1 各跑 1 次真实模型，检查配置生效、计量完整、grader 独立。
3. 再对 5 条开发任务各跑 S0/S1 一次，检查困难度、超时、环境成本、摘要触发情况。
4. 只在开发集调整预算、提示词和阈值，保留调整记录。修复任务或隐藏测试后重新执行 preflight。
5. 冻结正式版本和协议；开发集不并入正式结果。

正式单 Agent 实验为 `20 题 × 2 组 × 3 次 = 120 个 trial`。先用开发集估算两组平均费用及高开销案例，再决定是否能承担完整实验。

计费包括摘要、重试、续写、子调用；缓存按提供商实际规则计算，保存价格表版本。没有可靠 usage 或价格时，报告缺失，不填写猜测金额。预算不足就预先缩小实验；中途停止须列出未运行任务，不能将已完成子集包装成完整集合。

## 11. 第九步：正式运行单 Agent 对照

1. 在 manifest 展开 task × profile × repetition 的全部 trial_id。
2. 按任务和重复编号分块，随机或交替安排 S0/S1 顺序，保存顺序生成 seed。它只复现实验顺序，不保证模型输出确定。
3. 首轮外部 trial 并发为 1，固定缓存策略并记录实际命中量。依赖镜像可复用，工作目录、Memory、SQLite、消息历史不能复用。
4. 每次结束立即冻结证据；全部运行后统一汇总，不挑最好的一次。
5. 检查应有的 120 条记录、状态和证据完整性。
6. 分析失败，再提出新版本。根据正式结果调参后，应使用新 holdout 验证；旧集上的后续结果标为迭代回归。

超时、模型失败、工具失败、Agent 破坏环境均保留。平台 outage、基线环境损坏等基础设施异常也保留；可另报告排除它们的辅助结果，但必须列出分母和案例。

重跑遵循事先固定且对两组一致的规则，新 attempt 关联原 trial，不覆盖失败。grader 有 bug 时，修复后重判所有受影响候选并保留版本；若需重新调用 Agent，另建实验。

验收：任务、重复次数、profile、分母与原记录完全对应，没有基于成功与否选择性重跑。

## 12. 第十步：长上下文专项

建议 8 个任务、两种配置、每题 3 次，共 48 个 trial，等主评测稳定后再做。

### 12.1 怎样设计任务

1. 预先写出必须保留的早期约束，例如 API 签名、退出码、参数默认值、禁止修改目录。
2. 让任务经过多文件阅读、大搜索结果或较长工具输出后再完成代码修改。
3. 用隐藏测试验证早期约束和最终功能，不能只检查摘要有没有关键词。
4. 开发阶段确认实际触发压缩；正式阶段不触发的题也保留，报告触发覆盖率，不能看到结果后剔除。

两种实验形式分开：固定历史前缀后继续执行，用于较可控地测压缩；自然长任务完整运行，用于测实际效果。人为降低阈值的实验标为压力测试，不冒充生产默认配置效果。

### 12.2 对照与指标

要测历史压缩本身，就固定输出治理、恢复策略等其他设置，仅改变历史压缩开关；这不是直接复用 S0/S1 组合对照。反应式超限恢复也必须显式决定是否属于本次处理。

记录触发原因、generation、压缩前后字符数、摘要耗时与用量、摘要后重复读取次数、早期约束通过率、最终成功率及整个 trial 总消耗。

字符压缩率只表示消息体缩短，不等于 token 节省率。总消耗必须包含摘要模型和后续重读。若摘要缩短了上下文却增加总费用或降低成功率，应按事实报告这个取舍。

## 13. 第十一步：多 Agent 分两层评估

### 13.1 T1：固定 DAG 的调度收益

先准备 6 个固定 DAG，包含可并行任务、部分依赖任务和不能明显并行的串行对照。DAG 只有工作说明、依赖和资源声明，不包含参考答案。

对同一 DAG 分别运行 worker 并发 1 和 3，各重复 3 次，共 36 个 trial。两组使用相同 Team runtime、模型、总预算、任务定义、验收和审批策略，不要拿“无 Lead 的直接执行”与“完整 Team”混为一个并发实验。

落实到当前代码时，同时核对 `max_teammates`、计划批准的 teammate 数量等有效配置。保持 supervisor 线程池配置相同，记录实际 worker 峰值；当前线程池还可能承担 Lead/验证工作，不能把线程池大小直接叫 worker 并发数。

对预定义低风险审批用固定策略自动批准，记录决策；遇到策略外需求记为需人工或阻塞，不临场替某组解决问题。

T1 主计时从已批准 DAG 开始，到全部候选补丁冻结并完成约定验证结束。它证明调度/并发效果，不证明模型自主拆解质量。首次只选择不要求中途先集成代码才能继续执行的任务；有此要求的任务另立协议。

### 13.2 T2：完整协作流程

从同一自然语言需求出发，对照单 Agent 与完整 Team，在相同全局预算下衡量拆解、调度、通信、返工和最终产物。Team 没成功提交有效计划，也属于端到端失败，不能预先删掉。

记录两个时间：

- `candidate_ready_ms`：从交付需求到全部候选就绪，包含规划、审批、等待、返工和约定验证。
- `delivery_verified_ms`：从交付需求到最终代码组合后通过独立 grader。

人工审批、人工集成的参与方式必须预先定义，次数和耗时单列。不含最终集成的测量只能称“候选产物就绪时间”，不能叫“端到端交付耗时”。

### 13.3 集成能力边界

当前实现不等于自动合并所有候选。现有集成核验主要判断 ancestry/patch 等价关系，也不替代合并后的功能验证。

评测器可在独立临时工作区按固定拓扑顺序机械应用候选，再执行隐藏测试。这是评测侧的集成步骤，不是产品已有自动集成功能。应用冲突、缺少所需文件或最终测试失败都不算无人辅助完成；不得人工修完后继续记成功。

如果实验允许人工集成，应单独标为 assisted，并记录人做了什么。对于后续任务必须依赖上游已集成代码的流程，不能假设当前 worker 工作区已自动更新。

### 13.4 需要记录的额外字段

任务数、DAG 边数、可并行宽度、实际并发峰值、排队时间、审批等待、各 worker 耗时、消息数、返工次数、冲突数、验证耗时、候选 hash、lease 状态和不确定写入事件。

汇总所有 worker、Lead、摘要及后续独立 run_id 的调用。一次主任务下面有多个候选，不代表完成了多个独立用户任务。

## 14. 第十二步：统一计算指标

### 14.1 成功率与重复运行

每次运行定义：`success = functional_pass AND policy_pass AND budget_pass AND protocol_valid`。额外保留各分项，不用一个布尔值掩盖失败原因；分项仍未知时不能直接记成功。

每题重复 K 次时，先算该题成功次数/K，再对 N 道题取平均；在每题都完成相同 K 次的情况下，它等于成功 trial 数/(N×K)。未开始的任务不假装失败或成功，单独报告完成覆盖率；已开始的基础设施异常在主运行成功率中不计成功，另列排除它们的辅助口径。

区分：

- 单次尝试成功率的重复估计：所有独立尝试一起计算，不选最好一次。
- 三次至少成功一次的任务覆盖率：另一个指标，需要三倍尝试预算，不能冒充单次成功率。
- 提升百分点：`100 × (p_new - p_base)`；相对提升比例：`(p_new-p_base)/p_base`，基线为 0 时不计算。

小样本先报告 `成功数/总数`，不要只写看似精确的百分比。三次重复不是三道独立任务；不能把同题的 60 次尝试当成 60 个独立任务样本。

### 14.2 时间与并发

主要报告任务成功率和耗时分布，避免更早失败的方案显得更快。成功样本耗时要同时标出其成功样本数。

对两组共同成功的 task/repetition 配对计算 `speedup = T_serial / T_parallel`，汇总配对加速比中位数，并报告共同成功覆盖率及两组完整成功率。不能仅挑并发组成功的任务。

按定义区分环境准备、候选就绪、最终验证、人工等待等时间。并发调用耗时之和不等于墙钟时间，不能相加得出端到端时长。

首批 20 题不主打 P95。可报告中位数、四分位数、最慢案例和完整分布。需要不确定性区间时，按任务配对重采样；同题重复需一起保留，并说明仓库数量少限制了泛化结论。

### 14.3 模型调用、token 与费用

按唯一 call_id 汇总整个 trial 的主模型、摘要、重试、续写、worker 和 Lead 调用。分别记录逻辑调用和底层 HTTP 尝试，失败调用也保留；缺失 usage 不是消耗为 0。

保存提供商原始 usage 与规范化字段，明确 input、output、cache read、cache creation 是否互斥，核对后再求和，不能重复加缓存 token。报告 usage 完整调用数/全部逻辑调用数；必要时用事件与客户端账本交叉检查，避免分母本身漏记。

两个成本指标不能混淆：

- 成功样本平均费用：只对成功 trial 的费用取均值，存在条件选择。
- 每成功一次的实验摊销费用：全部 trial 已知费用之和/成功 trial 数，包含失败成本；零成功时为 N/A。

usage 不全时，已知费用只是下界，不能给出精确成本节省率。相同问题也适用于模型服务账单中无法归属到 trial 的消费。

### 14.4 压缩、安全、恢复指标

| 指标 | 定义与限制 |
|---|---|
| 单次字符压缩率 | `1 - 压缩后消息字符数/压缩前消息字符数`；固定消息序列化口径 |
| 总 token 降幅 | 对预定义配对任务比较全部调用用量；与成功率、usage 完整性一起报告 |
| 早期约束保持率 | 被最终固定验收满足的早期约束数/适用约束数；也报告全部约束同时满足的任务比例 |
| 策略决策正确率 | 决策与人工预标注 allow/ask/deny 一致的案例数/适用案例数 |
| 危险操作执行前防护率 | 按策略必须拦截或先确认的操作中，在未获授权时没有产生副作用的案例比例 |
| 正常操作误拒绝率 | 正常允许案例中被 deny 的比例；多余 ask 另算 |
| 故障恢复率 | 可恢复故障中，在限次/限时且满足最终验收条件下恢复的比例 |
| 故障处理正确率 | 所有适用故障中，实际终态、尝试数和副作用与预期相符的比例 |
| 重复副作用 | 指定注入用例中超出预期的实际副作用次数，并附受影响案例数 |

“100 条中通过 100 条”只支持这个有限集合上的结论，不能写“所有危险操作 100% 拦截”。执行后检测不算执行前防护；人工确认后的正常执行也不是绕过。

## 15. 可选扩展：不要同时把所有能力都做成主 benchmark

### 15.1 Memory

固定独立的写入阶段和后续新会话任务。保存每条记忆的正确性、相关性、时效性标签，包含无关记忆、已过期规则和相互矛盾规则。禁止把测试答案直接写入 Memory。

在相同后续任务上对照关闭/开启记忆；记录最终成功率、约束遵守、错误记忆引用和额外成本。有标注相关集合时才计算检索 precision/recall，空分母为 N/A。短任务没有改善也属于有效结果。

### 15.2 Skill Loading

设计确实需要项目流程知识的任务，固定技能版本。分别测技能选择正确性、加载后遵守率、最终完成率与加载开销；加入“无需 Skill”和“存在名称相近但不适用 Skill”的负例。

### 15.3 MCP

先用本地模拟 MCP 服务验证 schema 映射、超时、取消、断连、错误回传、读写权限及副作用审计，再对确有外部工具需求的任务测成功率。工具连通不等于任务完成。不要在真实邮件、生产数据库或付费服务上执行破坏性评测。

### 15.4 公开基准：SWE-bench 子集

等私有 runner 稳定再接入，不建议第一步就同时处理大型仓库环境与评测器问题。

1. 固定公开数据集名称、revision 和 instance_id 列表，事先选择子集及选择理由。
2. 按官方 harness 准备环境，在指定基线提交运行 Agent，输出候选 patch。
3. 导出官方预测格式所需的 `instance_id`、`model_name_or_path`、`model_patch`。
4. 使用官方 harness 的容器化测试验证候选；每次新实验使用独立 run_id，避免复用旧结果。
5. 保留官方报告与环境失败，不以自己的 grader 分数冒充官方成绩。

可参考官方命令结构，具体参数以固定版本为准：

```text
python -m swebench.harness.run_evaluation --dataset_name princeton-nlp/SWE-bench_Lite --predictions_path <预测文件> --instance_ids <预先固定的实例列表> --max_workers 1 --run_id <本次唯一标识>
```

容器准备、补丁评估和参数说明见 [SWE-bench 官方评估指南](https://www.swebench.com/SWE-bench/guides/evaluation/)。在 Windows 上需先验证适配的容器/WSL 环境，不把基础设施失败归为模型无法修复。

只测部分题，就写“在 SWE-bench Lite 的固定 N 题子集上”，不能称完整榜单成绩。公开题可能被模型训练接触，不能据此承诺无数据污染；自建题也只能说明自己的数据隔离方法。

### 16.1 拟实现的命令入口

以下是接口设计，不是当前可运行命令。先实现 E03–E07，再开放这些入口；不要现在直接照抄执行。

```text
python -m evals validate --dataset evals/datasets/dev/manifest.json
python -m evals preflight --dataset evals/datasets/dev/manifest.json
python -m evals run --dataset evals/datasets/dev/manifest.json --profiles S0 S1 --repeat 1 --fake-client --experiment fake-001
python -m evals run --dataset evals/datasets/dev/manifest.json --profiles S0 S1 --repeat 1 --experiment pilot-001

```

`validate` 只检查数据契约；`preflight` 验证基线与参考补丁，仅在可信准备环境读取私有答案；`plan` 只生成完整运行清单与预算估算，不花模型额度。真实执行入口应显示预估范围并要求显式预算配置。

`eval-data/` 是控制器侧路径示例，必须位于被测 Agent 无法访问的位置，而不是仅放在同一可读目录的另一个子文件夹。凭证也不能仅靠路径约定隐藏：控制器/模型代理持有凭证，执行器使用独立进程环境和网络权限；禁止把个人环境变量完整传给 Shell。

### 16.2 第一阶段做到什么就可以停

完成 E01–E12，就已经有一套可信的单 Agent 评估和可靠性测试证据。上下文、Team 可以分阶段补，不必一次跑满所有计划。

120 + 48 + 36 = 204 是三个预定真实模型实验的 trial 数，不包含开发试跑、可选 T2 和 Memory/Skill/MCP，亦不代表 204 次模型请求；一个 trial 通常包含多次请求。先估价再决定范围。

## 18. 如何用于 STAR 简历和面试

### 18.1 STAR 不要求每条都写一个百分比

- S：复杂开发任务需要多步工具操作，且面临长上下文、异常中断与并行修改冲突。
- T：独立构建可持续执行、可观测、可控制权限的开发 Agent 框架。
- A：围绕这些问题设计 Agent Loop、工具和 Hook、上下文治理、错误恢复，以及 DAG/Worktree/lease 协作机制。
- R：先写已实现并验证的交付物和能力边界；做完评估后，再补任务成功率、治理代价、并发收益等实测结果。

“已构建完整框架、打通指定场景、通过有定义的验证”也可以是定性结果，不需要为了满足 STAR 发明业务收益。

### 18.2 可留在个人简历草稿中的结果句

以下只能在完成相应实验后改成已完成表述；当前保留“待评估”标记。正式投递前没有数据就删掉结果占位，保留已实现内容。

> 面向多步软件开发任务中上下文膨胀与异常中断问题，独立设计并实现基于工具调用反馈闭环的 Agent 框架，统一工具注册、调度与权限 Hook；构建长上下文治理和有界恢复机制。拟在 __ 个仓库、__ 项固定任务上完成同模型、同预算对照，任务成功率由 __ 提升至 __，每成功一次的摊销 token/费用为 __（待评估）。

> 针对并行任务依赖与共享文件冲突，实现 DAG 调度、Worktree 隔离及 lease/结构化通信机制；拟在 __ 组固定 DAG 上对照单 worker 与 __ worker，报告共同成功配对的候选就绪加速比 __、最终验证通过率 __、总 token 开销变化 __（待评估）。

> 建设可复现评估和故障注入流程，覆盖 __ 条安全策略案例与 __ 条故障序列；策略决策符合率 __、正常操作误拒绝率 __、可恢复故障恢复率 __（待建设、待评估）。

最终简历选最能证明价值的 2–3 个指标，不把所有模块和测试数都挤进去。若只做 T1，就不写自主规划收益或端到端自动交付；没有实测提升，就写真实能力和实验发现。

### 18.3 面试证据包

准备一份可脱敏展示的文件夹：固定任务清单、冻结配置、运行 manifest、自动生成的汇总、两个成功和两个失败的轨迹/patch/测试报告，以及一页能力边界说明。原始凭证、个人路径、无权公开的仓库代码不进入分享包。

| 追问 | 应当能展示的证据 |
|---|---|
| 任务怎么来的，会不会只选有利的题？ | 来源、类别、预先冻结的清单、开发/正式划分 |
| 怎么确定真的完成？ | 独立 grader、基线失败与参考补丁通过、固定回归、新文件重放 |
| 提升来自模型还是框架？ | 同模型/profile diff、预算口径、消融；组合实验不归因到单模块 |
| 失败是不是重跑后删掉了？ | 全量 trial_id、原失败及关联重跑记录 |
| 多 Agent 快了但贵多少？ | 所有 worker/Lead/摘要账本、成功覆盖率、候选与最终交付计时 |
| 安全与恢复到底保证什么？ | 注入点、实际副作用、拦截/写后检测区别、未知结果处理和未覆盖边界 |

合理目标不是“保证面试官问不出来”，而是每个结论都有证据、每个边界都能解释。一个没有达到预期但分析清楚的对照实验，也比无法复现的漂亮提升数字更能体现工程能力。
